## Deviations from the plan text (and why)
1. **CSRF header is required on `api/v1` only, not every `/api/*`.** The Razor pages' jQuery calls the legacy `/api/*` controllers without it; requiring it would break the live UI. Z.4 makes the check the only gate for everything.
2. **There is no lockout.** The plan says "rate-limit and lockout exactly as AccountController"; `AuthService` has neither a failed-attempt counter nor a lock. The only protection is the IP throttle, which I tightened for this endpoint
   (`post:/api/v1/auth/login`, 10/min, `appsettings.json`) - the global 100/min would allow all 10 000 four-digit PINs in ~100 minutes. A real per-user lockout is a change to `AuthService` + a migration -> parking lot (found by 0A).
3. **Licence gating for `api/v1` is an attribute, not middleware.** `LicenseEnforcementMiddleware` still matches the legacy URLs only. P1/P4 put `[RequireSalesLicense]` on checkout / hold / resume. Services keep their backstop check.
4. **`Accept-Language` is honoured for `api/v1` only.** Chromium sends one on every XHR; letting it win on the legacy `/api/*` would flip the Arabic Razor UI's server messages to English.
5. **Page error handlers (`UseDeveloperExceptionPage` / `UseExceptionHandler`) now skip `api/v1`.** Otherwise they swallow the exception before the JSON handler sees it (the old `{success:false}` branch of `ExceptionHandlingMiddleware` is dead code for the same reason).
6. `GET auth/sign-in-options` was not in the plan but the login screen needs the name picker; it exposes exactly what the Razor login page already shows (active usernames + display names).
7. The 429 body is now problem JSON with `code: rate_limited` for **all** endpoints (AspNetCoreRateLimit has one global response); legacy callers got a plain-text message before.
8. The cookie challenge answers JSON for **all** `/api/*`, so a legacy `/api/*` call without a cookie gets 401 JSON instead of a 302 to the login page (jQuery XHRs already got 401).

## For the next tracks
- Pick an access declaration for **every** action (`[RequirePermission]` ... or `[AnySignedInUser]`); a test fails otherwise. Copy the old controller's permission per action.
- Add `[RequireSalesLicense]` to sale-changing actions. Return `ConflictFailure("drawer_not_open", msg)` etc. for business refusals - the SPA branches on `code`.
- A 401 from `auth/login` means wrong PIN, not an expired session: the client's global 401 handler must not redirect from the login page.
- `session.nav[].spaPath` is the route the SPA must register for a page (`/app/cash-drawer`), migrated or not; flip the one line in `SpaMigration.Migrated` when the page ships.
- Money: nothing here decides amounts. `DrawerStatusDto.OpeningCash` is a `decimal` (OpenAPI `number`); the UI formats with the shared money helper.
- `schema.d.ts`/`permissions.ts` are generated: on conflict take either side and `npm run api:types -- --no-build`.

## What to verify by hand
1. `cd client && npm run api:types` -> files unchanged (deterministic). Needs the .NET SDK; closing Visual Studio's debugger is not required (it runs `dotnet run` from `Web/`, which only fails if it must rebuild a locked `Web\bin`; use `-- --no-build` then).
2. Run the app (Development) and open `/swagger`: only `auth` and `session` tags. Try login with the `X-NexPOS-Client: web` header (Swagger UI cannot add it for you - use curl or the generated client).
3. Razor rail and Ctrl+K palette still link to the Razor pages in EN and AR (links are unchanged until a module flips `SpaMigration`).
4. Sign in on a Razor page, then `curl -b` the cookie against `/api/v1/session`: the same cookie works both ways.
