# 0E — i18n pipeline: handoff notes

**Branch:** `react/0E` (rebased on `react/main` after 0C/0F landed). **Status:** ☑ done.

## What exists
- **`npm run i18n:export`** (`client/scripts/export-locales.mjs`, logic in `scripts/lib/locales.mjs`) converts the old app's
  translations into `client/src/locales/{en,ar}/<namespace>.json`. Re-runnable; keys and values copied verbatim.
  - `Web/Resources/SharedResource.{en,ar}.resx` → namespace **`common`** (821 keys + the 41 from `js/locales` `common`).
  - `Web/Resources/Views/<Folder>/*.{en,ar}.resx` → namespace = folder, lower-camel: `pos`, `orders`, `cashDrawer`,
    `auditLogs`, `productDisplayOrder`, … (`Views/Shared` → **`layout`**). All views of a folder are merged.
  - `Web/wwwroot/js/locales/{en,ar}.json` → one namespace per top-level section (`pos`, `dashboard`, `products`,
    `notifications` merge into the view namespaces of the same name; `alerts`, `validation`, `print`, `datatable` stand alone).
    Nested paths are flattened with dots: the old `i18n.t('pos.cartIsEmpty')` is key `pos.cartIsEmpty` in namespace `pos`.
  - Result today: 24 namespaces, ~2380 keys per language.
- Flags: `--check` (write nothing, exit 1 if files are stale — use before merging), `--prune` (also delete keys/namespace
  files no source defines), `--strict` (exit 1 if a key is in only one language), `--verbose`.
- **Merge, not overwrite.** Keys a track hand-adds to `locales/*/<ns>.json` survive a re-export (section 9: "add them to both
  languages in the same commit"). A key that *does* exist in a source is always overwritten by the source, so edits to the
  `.resx` flow through. Use `--prune` only when you want hand-added keys gone.
- **Runtime** `client/src/core/i18n/`: `index.ts` (i18next + react-i18next, lazy backend, `setLanguage`, `seedLanguage`,
  `loadNamespaces`), `languages.ts` (no i18next import — `getLanguage()` is what the API client sends as `Accept-Language`),
  `format.ts`, `useLanguage.ts`. `main.tsx` imports `@/core/i18n` once for the side effect.
- **`npm run i18n:lint`** (also part of `npm run lint`): every literal `t('Key')` / `i18n.t('Key')` / `i18nKey="Key"` in
  `client/src` (not tests, not comments) must exist in `locales/en`; keys missing from `ar` are a warning (`--strict-ar` fails).

## How to use it in a module
```tsx
const { t } = useTranslation('orders')        // namespace = the hook argument; downloads the chunk with the route
t('OrdersManagement')                          // key = the .resx name, verbatim
t('PackOf', { 0: 12 })                         // placeholders are i18next's {{0}} / {{name}}
t('Total', { ns: 'common' })                   // a key from another namespace
```
- Pre-load with the route to avoid a Suspense waterfall: `loader: () => loadNamespaces('orders')`.
- Switching: `await setLanguage('ar')` → writes `localStorage['nexpos.lang']`, sets `<html lang dir>`, re-renders.
- First visit: call `seedLanguage(session.language)` after the session bootstrap (0D) — the old app's culture cookie is
  HttpOnly so the SPA cannot read it; the server can. A stored choice always wins.
- When two views of a folder define the same key with different text (10 cases, e.g. `orders` → `Total`, `Items`;
  `receipts` → `Customer`, `Cashier`, `Status`) the bare key is the first view's text and **every** variant is also
  available as `<View>.<key>` (`Receipt.Total`) in both languages. Prefer the prefixed key when the screen maps to one view.

## Decisions (answers known-unknown #3)
- **Digits are Western (0-9) in both languages.** The old JS formats every number/money with `'en-US'`, and .NET never
  substitutes digits on receipts/PDFs; the one outlier (the dashboard clock using `document.lang` → Arabic-Indic digits in
  `ar`) is treated as a bug, not a requirement. `core/i18n/format.ts` uses `en-US` and `ar-u-nu-latn`. Month/weekday names
  follow the language. 0C's `formatMoney` should build on `formatFixed`/`intlLocale()`.
- **No pluralisation.** Neither the `.resx` files nor `localization.js` has plural forms ("{0} minutes"); we mirror that.
  If a screen truly needs one, use i18next `_one`/`_other`/… suffix keys with `count` — Arabic's six forms are supported
  by `Intl.PluralRules` — but add the keys by hand to both languages.
- **Separators are disabled** (`keySeparator: false`, `nsSeparator: false`) because 800+ keys are English sentences with dots
  and colons ("Signing in..."). So `ui/` keys are flat keys that literally contain a dot: `t('common.close')` is the key
  `common.close` in namespace `common`, not a nested path.
- **Placeholders:** the exporter rewrites the old `{0}` / `{name}` to i18next's standard `{{0}}` / `{{name}}` (the only change ever
  made to a value; `${0}` and an existing `{{x}}` are left alone). Standard syntax because 0C's components and defaults already use it.
- **0C's `ui/` keys are seeded:** the 38 `common.*` keys listed in `docs/react-migration/notes/0C.md` (with Arabic, taken from
  `ui/kit/kitI18n.ts`) are in `locales/{en,ar}/common.json`. They are hand-added (not in any `.resx`), so the export keeps them.
  `kitI18n.ts` can stay for `_kit` and tests; its text now matches the real files.
- A key present in only one language is **not** copied into the other file; `fallbackLng: 'en'` fills the gap. Today:
  `common/All Products` (no ar), `common/AllProducts` (no en), `dashboard/failedToLoadChartData` (no ar).

  `npm run i18n:export` and commit the result when you (or anyone) edit a `.resx`.
