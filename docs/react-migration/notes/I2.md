## Endpoints
`GET feed?take=` (1–50, default 5) → `{unreadCount, items[]}` · `POST feed/{alert|notification}/{id}/read` · `POST read-all` · `GET summary` · `GET ?page&pageSize&dir&q&kind&unread` · `POST {id}/read` · `DELETE {id}` · `DELETE` (clear all) · `POST cleanup` · `GET alerts?…&kind&scope=open|closed|all` · `POST alerts/{id}/dismiss` · `POST alerts/dismiss-all` · `DELETE alerts/{id}`.
Permissions: notifications = any signed-in user (the Razor controller only had `[Authorize]`); `GET alerts` = `Alerts.Read`; dismiss / dismiss-all = `Alerts.Update`; delete alert = `Alerts.Delete` (the keys the legacy `api/Alerts` controller already used). The bell feed, the summary and read-all silently leave alerts out for a caller without `Alerts.Read`; acknowledging an alert from the bell is 403 for them.

## Decision: live refresh is a 30 s poll (no SSE)
The bell polls `GET feed` every 30 s and on window focus (`refetchInterval` in TanStack Query, which also pauses while the tab is hidden); the page's lists and tiles poll at the same rate. Reasons: the Razor bell already polled at 30 s and nothing else needs sub-second delivery (alerts come from a sale or a stock check); SSE would hold a connection open per tab on a counter PC and needs its own auth / licence / shutdown handling for no visible gain. Every change on the page also invalidates the session query, so the badge from `/session` and the rail stay in step. If push is ever wanted it belongs to the parking lot with SignalR.

## Differences from the Razor page
1. **One list, one tab per concept.** The Razor page had Notifications / Alerts / Recent tabs; "Recent" was just the newest 10 notifications and is dropped (the list is newest-first already). The page now has real paging (25 per page), search, an "unread only" filter, and for alerts an Open / Closed / All scope (the old tab showed every status mixed).
2. **Alerts are worded from their product facts** (`kind` + `params`), exactly like the bell already did, not as the stored English. An alert without the facts (made by hand) shows its stored title / message. Notifications keep their stored text — it is written in English by whatever raised it, so an Arabic user sees English there (same as before).
3. **Alert permissions are enforced.** The Razor page let any signed-in user dismiss / delete alerts through `NotificationsController`; the SPA needs `Alerts.Read` to see the tab and `Alerts.Update` / `Alerts.Delete` for the buttons, matching the legacy `api/Alerts` controller. A cashier loses nothing they could see in the nav, but they no longer see alerts at all (the old page showed them).
4. **Dropped:** "Refresh" button (lists refetch on change, focus and every 30 s), "System status: OK" tile (hard-coded text, no data behind it), "Refresh inventory alerts" (a "coming soon" toast), the "critical" count (the old service treated every active alert as critical), and the Razor "notification settings" / create-notification / create-alert endpoints (nothing in the UI called them; they stay on the Razor controller until Cutover). Added in their place: tiles for total / unread, active / open alerts, low stock / out of stock, and a "View low stock items" link (to `/app/inventory/low-stock`).
5. **Clear all** deletes every notification (as before) after a confirm. **Cleanup** = notifications older than 30 days + alerts dismissed more than 7 days ago; it never deletes an alert somebody still has to deal with.
6. **Marking read twice keeps the first read time** (the old `MarkAsRead` rewrote it).
7. Unknown `kind` / `scope` filter → 400 `validation_failed` on that field (numbers are refused too).
8. Deleting / dismissing / reading something that is gone → 404 (the old controller answered `{success:true}` for a missing id or threw).

## Bell behaviour kept from the Razor script
Unread badge (9+), newest five items, click = mark read + open the thing, "mark all read", toasts: ≤ 3 per poll, 6 s, once per key, remembered in `localStorage['nexpos-notification-toasts-seen']` (same key as the Razor script, so moving between old and new pages does not repeat toasts); toasts are suppressed while the dropdown is open. Link of a stock alert: Product details (`/app/products/:id` once Products is migrated — it is — otherwise the Razor URL); anything else opens the notifications page. Until the first feed answer the badge shows the count from `/session`.

## Watch list (pre-existing, not changed here)
- `NotificationService.GetFeedAsync`, `MarkAllReadAsync`, `ClearAllNotificationsAsync` etc. act on **all** notifications, not on the current user's: `Notification.UserId` is never set by anything, so notifications are shared by everyone. Marking one read marks it read for everyone.
- `NotificationService.GetFilteredNotificationsAsync` / `GetFilteredAlertsAsync` (Razor) still load every row then page in memory; the SPA does not use them. `GetNotificationStatsAsync` likewise.
- The Razor top bar's `notifications.js` and the Razor page remain until Cutover; they work untouched.
- Alert raising is in `StockAlertService` after a sale (`Application`, not touched). Its English title / message are what an Arabic user sees on a hand-made alert.
- `Notifications_View` / `Notifications_Manage` permissions exist but nothing checks them (the nav entry has no permission either).
