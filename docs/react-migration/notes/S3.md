## Endpoints
`GET customers` (page/pageSize/sort=`name|email|phoneNumber|address|ordersCount|totalSpent|balance|isActive`/dir/q — q matches name, email, phone) · `GET customers/summary` · `GET customers/{id}` · `POST customers` · `PUT customers/{id}` · `DELETE customers/{id}` (409 `customer_has_balance`) · `GET customers/{id}/debt-transactions` (paged, newest first) · `POST customers/{id}/debt-transactions {amount, customerOwesMore, note}` → `{transaction, balance}` · `GET customers/export` (CSV).
Permissions copied from the Razor controller: `Customers.View` (everything that reads, incl. export) / `.Create` / `.Edit` (update **and** debt entries) / `.Delete`.

## For P4: `<CustomerDebtDialog>`

## Decisions / differences from the Razor pages
1. **Create/edit is a dialog** (as in C2), not the separate Create/Edit pages. Details is a route.
2. **Dropped form fields:** Date of birth, Company name, Tax number, Notes and the "company customer" checkbox were on the Razor forms but the controller never stored them (the entity has no such columns). The "Company customers" tile was a hard-coded 0 and is gone; it is replaced by **Outstanding debt** (sum of positive balances + how many customers owe), which the data supports. City / country / postal code have no input anywhere; the details page shows them if present and edits keep them untouched.
3. **Purchases exclude cancelled and returned orders everywhere.** The Razor list did; the Razor details page counted *all* orders in "Total orders / Total spent / Average order". The SPA uses the list's rule on both. The order history table still shows every order with its status badge, and `allOrdersCount` feeds "View all orders (n)".
4. **Mixed currencies:** Total spent adds `Order.TotalAmount` as stored, whatever the order's currency, and shows it in the default currency's notation — as the Razor pages did. Order rows on the details page show their own currency. Converting is a money-rule change, left out (see watch list).
5. **Debt ledger is paged** (10 per page) instead of "last 20 + showing recent N".
6. **Overpayment:** unchanged — there is no cap. Paying more than is owed leaves a negative balance ("I owe the customer"). The dialog now shows the balance after the entry and says so in words before saving when it would go below zero (display only; the server decides).
7. **Search** also matches "first last" as one phrase (Razor matched first name, last name, email, phone separately).
8. **Delete** with a non-zero balance (either direction) is 409 `customer_has_balance`; the sentence comes localized from the server and is shown inside the confirm dialog. Customers with order history can be deleted (soft delete) once settled.
9. **Validation** repeats the DTO attributes (name 2–100, email ≤ 255 and valid, phone ≤ 20, address ≤ 500) and additionally measures names *after trimming* (the Razor attributes saw the untrimmed text). Empty email is stored as `""` as before (column is non-null) and returned as `null`.
10. Export is a GET (the Razor one was a POST with an antiforgery token). Refresh buttons are gone: lists refetch on mutation, focus and every 30 s.
11. Order links go through the session nav: `Orders` href `/app/…` → `/app/orders/:id` (assumes S1 uses that shape), otherwise the Razor `…/Orders/Details/:id`. "View all orders" is `<orders href>?customerId=`. The Razor Orders page may ignore `customerId` — S1 should read it (same note as C2's `categoryId`).

## Watch list (pre-existing, not changed here)
- **No default role holds `Customers.Delete`** (not even Admin), so the delete button is hidden/403 on a fresh install until the Users page grants it — same as `Categories.Delete`. The API tests grant it first.
- `Customers_Manage` exists but nothing checks it.
- `Customer.Email` is non-null with no uniqueness rule; the Razor guideline text "emails must be unique" is not enforced anywhere.
- Mixed-currency "total spent" (decision 4) and `CustomerDebt` balances being in the default currency only: a debt sale in a non-default currency is converted by the POS (P1), not by this module.
- The Razor list loaded every customer *with every order*; the API loads customers plus two columns of the orders and pages in memory (fine into tens of thousands; move to SQL paging if a store grows past that).
