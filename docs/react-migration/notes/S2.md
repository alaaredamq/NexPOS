## Endpoints (`Sales.View` unless noted — same as the old class-level attribute)
`GET current` (status + open session with running figures) · `POST open {openingCash, notes}` (201; 409 `drawer_already_open`) · `GET sessions?page&pageSize&from&to` (the user's own sessions, local dates `yyyy-MM-dd`) · `GET sessions/{id}` (404 `session_not_found`) · `POST sessions/{id}/close {actualCash, notes}` **Sales.Edit** (409 `session_closed`) · `POST sessions/{id}/drops {amount, reason, notes}` **Sales.Edit** (201; 409 `session_closed`) · `GET sessions/{id}/z-report` (409 `session_still_open`, 409 `z_report_unavailable`) · `POST sessions/{id}/z-report/print` (never fails because of the printer: `printed:false` + message + PDF link) · `GET sessions/{id}/z-report.pdf` (A4).

## `useDrawerStatus()` (the shell chip and the till)
`modules/cash-drawer/useDrawerStatus.ts` reads `session.drawer` from the bootstrap payload. I did **not** edit `shell/DrawerChip.tsx` (frozen; the chip already reads the same field, and a shell → module import would point the wrong way). The chip and the till therefore share one request (the 60 s session refresh + focus). Open / close / drop here also refetch the session, so the chip flips at once (checked in Playwright). Three endpoints share the shape `{isOpen, sessionId, openingCash, openedAt}`: `session.drawer`, `GET pos/drawer` (P1) and `GET cash-drawer/current`.
**For P4:** "open your drawer first" can link to `/cash-drawer/open?returnTo=/pos` — after opening, the page returns the cashier there (same-app paths only).

## Decisions / differences from the Razor pages
1. **No opening float per currency.** The plan said "per currency"; the table has one `OpeningCash` column and D-rules forbid a schema change. The drawer stays a single dollar amount, as the Razor pages, the printed Z report and the chip all show it (`$` is a constant in `api.ts`).
2. **Dropped:** `GetAllOpenSessions` (no caller anywhere in the old UI) and `GetSessionSummary` (folded into `GET sessions/{id}`). The old `Open` / `Close` / `History` / `ZReport` MVC pages map to the five SPA routes.
3. **Counting 0 is allowed.** The old close page rejected 0 (`!actualCash`) although the server accepted it; a drawer emptied by drops legitimately counts 0. The API rejects only negatives.
4. **New server-side validation** of what the old page only checked in JS: opening/actual ≥ 0, drop amount > 0, notes ≤ 1000 chars. Errors are 400 `validation_failed` with `errors{}`.
5. **After closing** the SPA goes straight to the Z report in the same tab; the old page opened it in a new tab and sent the cashier to the dashboard. The "difference > 5 with no notes → confirm" rule is kept (`drawerMath.ts`, tested).
6. **History is paged** (default 25) instead of returning every row; the 30-day default range is kept.
7. A closed session shows the figures **stored at closing** (an order voided afterwards does not rewrite a closed day); an open one shows the running figures.
8. Cash-drop reasons keep the English values the old page stored (`Safe Deposit`, `Bank Deposit`, `Excess Cash`, `Other`); the UI translates those four and shows anything else as typed.
9. The Z report page also lists the drops on the main page (small table under the tiles) — the data was already in the response.
10. Printing is server-side (D11): print uses `ReportDocuments.ZReport` + `IThermalPrinterService`, PDF is A4, both write the same `Print` / `PrintFailed` / `PdfGenerated` audit rows the Razor controller wrote.

## Watch list (pre-existing, not changed — business-rule decisions for the owner)
- **Expected cash counts every sale as cash.** `CashDrawerService` adds *all* non-cancelled order totals to expected cash (`// TODO: filter by payment method`), so card sales, on-account (debt) sales and foreign-currency sales inflate it; `CardSales`/`OtherPayments` on the Z report are always 0 and every order says "Cash". The numbers the SPA shows are exactly what the Razor page showed.
- **Net sales is gross minus discounts**, but "gross" is the sum of order totals, which are already after discount — discounts are subtracted twice. My Z report test uses discount-free sales so it does not pin this.
- **Only Admin can use a drawer on a fresh install.** No default role other than Admin/SuperAdmin holds `Sales.View`/`Sales.Edit` (Cashier and Manager hold neither), so a cashier gets 403 here and the shell chip is hidden for them — as in the Razor app. The permission matrix test builds a `Sales.View`-only role to prove the split.
- Anyone with `Sales.Edit` can close or drop cash into **another user's** open session (the old action took any session id), and anyone with `Sales.View` can read any session or Z report. Kept for parity.
- Drawer endpoints are not behind the sales-licence gate (the old controller was not either); only checkout is.
- The Z report of a session closed by a very old version (null stored totals) answers 409 `z_report_unavailable` instead of a 500.
