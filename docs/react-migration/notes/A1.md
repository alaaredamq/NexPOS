## Endpoints
`GET users` (page/pageSize/sort=`name|username|email|role|isActive|lastLoginAt|createdAt`/dir/q) · `GET users/summary` · `GET users/{id}` · `POST users` · `PUT users/{id}` · `PUT users/{id}/active {isActive}` · `POST users/{id}/reset-pin {newPin}` · `DELETE users/{id}` (409 `user_in_use`).
`GET roles` (sort=`name|userCount|permissionCount|createdAt`, q = name/description) · `GET roles/{id}` (with `permissions[]`) · `POST roles` · `PUT roles/{id}` · `DELETE roles/{id}` (409 `role_system`, `role_in_use`; `PUT` on SuperAdmin 409 `role_super_admin_locked`; name problems 400 on `name`).
`GET account/profile` · `POST account/change-pin {currentPin?, newPin, confirmPin}`.
Permissions copied from the Razor controller: every `users` and `roles` action needs `Users.View` (the Razor class-level attribute) **plus** `Users.Create` (create) / `Users.Edit` (edit, enable/disable, reset PIN) / `Users.Delete` (delete) / `Users.Manage` (read or change a role's grants). `GET roles` (the list) needs only `Users.View`, as `GetRoles` did. The account endpoints are `[AnySignedInUser]`.

## Decisions / differences from the Razor pages
1. **Create/edit are dialogs**; users and roles are two routes (tabs), not one page with four tabs.
2. **Dropped: the "Active Sessions" tab.** `UserSession` rows are written at every sign-in but nothing ever reads them back: the cookie is not validated against them, sign-out does not close them, and the sign-in passes no IP / user agent. The tab therefore listed every sign-in of the last 24 h with "Unknown device", and **Terminate did not sign anybody out**. Showing it would be a lie; real session control needs a change to the cookie validation in `Program.cs` (frozen). Parking-lot item.
3. **Dropped: the static "Permissions" tab** (the catalogue with a per-role count). The role editor's matrix is the same catalogue, ticked per role; the roles table shows the counts.
4. **Dropped: the fake tile trends** ("+2", "vs last month", "Currently online") — they were hard-coded text. The four tiles are the real counts.
5. **Per-user permission overrides: none.** `UserPermission` rows exist in the model but `RoleAccessService.GetUserAccessAsync` reads the role only and no page edits them. Not ported.
6. **Disable and Delete are not offered on your own row** (UI only; the API does not forbid it). Disabling yourself signs you out on the next request; the Razor page offered it anyway.
7. **The role picker of the user forms is the live roles list** (`GET roles`), so a role added in the other tab is immediately selectable; the Razor page patched its `<select>`s by hand.
8. **Create user takes `roleId`** (the Razor create took the role *name*). Username is trimmed and cannot be edited later (as before); email uniqueness and PIN rules (exactly 4 digits) unchanged; first/last name are no longer required (the Razor form said `required`, the server never checked).
9. **PIN change screen:** one keypad, three fields (current / new / confirm), moving on when a field is full. **Right after an admin sets or resets a PIN the current PIN is not asked for** (`mustChangePin`) — the user has just typed it to sign in. The Razor form asked for it anyway, which made that case work only if the user remembered the PIN they had just entered; the server still refuses an unchanged PIN and writes `PinChangeFailed` for a wrong current one. Rules ("4 digits", "must differ", "avoid sequences") are the old texts; **the "avoid sequences" line is advice only, nothing enforces it** (as before).
10. **`mustChangePin` is now enforced inside the SPA:** `RequireAuth` sends every route except `/account/change-pin` there (it used to hand off to the Razor page with a full navigation). The user menu's Profile / Change PIN are router links.
11. **Profile page:** the Razor "Session information" card showed `new Date()` as the login time and a hard-coded IP `192.168.1.100`. Replaced by the real **last sign-in** from the user record. User id / role id are not shown.
12. **Self-lock warning:** unticking `Users.Manage` on the role you hold shows a warning in the editor (the Razor editor let you do it silently). Nothing stops it.
13. Audit: the requests are audited as `POST/PUT/DELETE Api.Users/...`; PIN set/reset/change and failed change write the same `PinChanged` / `PinChangeFailed` entries as before (from `UserService` / the account service). The Razor controller wrote no explicit entry for role or user edits (the entity change tracker records them), so none was added.

## Watch list (pre-existing, not changed here)
- **`Users.Create` / `Users.Edit` / `Users.Delete` are not implied by `Users.Manage`** (as on the Razor page): a role with only `Users.Manage` gets the role actions but none of the user buttons.
- Deleting a user goes through `UserService.DeleteAsync`, which turns a foreign-key failure (sales, receipts, debt entries, cash drawer records) into the 409 `user_in_use`; sign-in session rows cascade away with the user.
- No lockout in `AuthService` (the throttle is the only brute-force guard) — same note as 0A.
- `UserService.UpdateAsync` copies `LastLoginAt` from the passed entity; the API passes the entity it just read, so it is preserved.
- `ApiPipelineTests.The_session_carries_user_role_permissions_nav...` now uses **Settings** as its "not migrated yet" example; when A2 flips Settings it must pick another page (Backup is next).
