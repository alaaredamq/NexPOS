## Endpoints
`GET backups` (page/pageSize/sort=`createdAt`|`name`|`size`/dir/`q`/`status`) · `GET backups/summary` · `GET backups/{id}` · `POST backups` · `POST backups/{id}/restore` · `POST backups/{id}/validate` · `GET backups/{id}/download` · `DELETE backups/{id}` · `POST backups/bulk-delete` · `POST backups/bulk-validate` · `POST backups/cleanup` · `POST backups/test-connection`.
`GET|POST backup-schedules` · `PUT|DELETE backup-schedules/{id}` · `PUT backup-schedules/{id}/active` · `POST backup-schedules/{id}/run`.
`GET license` · `POST license/activate`.

Permissions (copied from the Razor controller, whose class-level `Backup.View` applies to everything): view/list/download/test-connection = `Backup.View`; create + run schedule now = `Backup.Create`; restore = `Backup.Restore`; validate, delete, bulk, cleanup, schedule edits = `Backup.Manage`. Licence = `License.Manage`. All permission rows are tested with limited roles.

## The licence trap (handled)
Neither controller has `[RequireSalesLicense]`, and the routes are not under `RequireSalesLicense`. The test host has no licence file (selling is stopped), and a test + the Playwright spec take, download and restore a backup and open the licence screen in exactly that state.

## Bugs fixed on the way (in shared code, so the Razor page benefits too)
1. **Two backups in the same second overwrote one file** (name has second resolution; a restore's safety backup right after a click, or a schedule firing as someone clicks). `GenerateBackupFileNameAsync` now numbers the later one.
2. **A restore left stale state:** the in-process `ICacheService` (dashboard, products) and the `AccessCache` (users/roles came back with the restore). The API clears both after a restore.
3. **After a restore the restored-from backup showed "In progress" forever:** the snapshot is taken while its own row says InProgress, and that row comes back with the table; EF also kept the pre-restore tracked row. The service now clears the change tracker after the restore and resolves in-progress rows immediately (grace 0) after a restore.
4. Bulk delete threw on an unknown id (second tab); the API skips unknown ids.

## Decisions / differences from the Razor page
1. **Restore asks first**, in a dialog that names the backup and says what is lost; the old page restored on one click. The dialog stays open with a spinner for the whole request (the server restores before answering) and shows a failure inside it. "Create backup before restore" stays on by default; unticked, the dialog says it cannot be undone.
2. **Progress is a busy state, not a progress bar.** The server runs backup/restore synchronously and answers when done (the old JS already relied on that for create; its polling path for restore never ran because `RestoreBackup` returned no `operationId`). So `GetBackupProgress`, `GetOperationStatus`, `CancelBackup/Restore/Operation` are **dropped**: nothing can be cancelled or polled mid-request.
3. **Dropped (listed per the DoD):** `Debug`/`DebugDirectories` (the folder + free space are in System information now), `GetDatabaseTables`, `GetSystemInfo`'s SQL-Server fields (the old JS read `databaseServer`/`databaseName`, which never existed), `GenerateReport` ("coming soon" in the old UI) and `ExportMetadata`, `CreateEmergencyBackup` / `GetEmergencyRestoreOptions` / `EmergencyRestore` ("Emergency" button said "coming soon"; restore with safety backup covers it), `GetBackupHistory`, `GetActiveSchedules` (the list has everything), `DownloadBackupPost`, `TestConnections` GET + `TestConnection` POST merged into one `test-connection`.
4. **Options that did nothing are gone:** backup type (SQLite only makes full snapshots; schedules are always `Full`), include data/schema, encrypt (placeholder), compression (not applied). The API always creates a full, uncompressed snapshot.
5. **Failed snapshot = 500 `backup_failed`** with the reason (the Razor action answered 200 `{success:false}`); the failed row is still recorded and listed. A restore that cannot run (file gone, not a backup of this database) is 409 `restore_failed`; unknown ids are 404.
6. **Download is a plain GET** (`PhysicalFile`, resumable, streamed) instead of reading the whole file into memory. 404 `backup_file_missing` when the file was removed. The DTO has `fileName`, never the server's full path.
7. **Schedule DTO is flatter:** `frequency`, `time` (`HH:mm`), `dayOfWeek` (0 = Sunday), `dayOfMonth` (1–28), `lastRunAt`/`nextRunAt`. A weekly schedule needs a day of the week and a monthly one a day of the month (400 with the field); the day that does not belong to the frequency is dropped.
8. **Reports tab → "System information" tab** (folder, free space, database size, total backup size) plus a reminder that a backup on the same disk does not survive that disk failing.
9. Licence: same fields and texts as the Razor page; a refused key is 400 `validation_failed` on `licenseKey` with the localized reason (Razor used TempData + redirect). A successful activation refreshes the session, so the banner and the sales routes follow immediately. The "SalesStopped" (`?from=pos`) page for cashiers is not a screen of its own: the shell's licence-stopped page (0D) already does that.
10. The list is paged in memory (the catalog is a few dozen rows; the service's own paging has no total). Status filter chips: All / Completed / Failed.

## Watch list (pre-existing, not changed)
- Backups are written to a `Backups` folder next to the database, **on the same disk**. Nothing copies them elsewhere; the System tab says so. A real off-disk target is a feature.
- `CreatedBy` is always `"System"` (a `TODO` in `BackupService`), so the list cannot say who took a backup. Audit rows are the record of who.
- A restore replaces the users table too: the restoring admin's own session survives only if their user exists in the backup. The UI refetches the session; a vanished user goes to the sign-in page.
- `ResolveStuckBackups` still treats an `InProgress` row older than 30 minutes (outside a restore) as interrupted.
- `[RequestSizeLimit(16 KB)]` on licence activation is Kestrel's; the in-process test host does not enforce it, so it is not tested.
