## Endpoints
`GET categories` (page/pageSize/sort=`name|description|isActive|productCount`/dir/q) · `GET categories/summary` · `GET categories/{id}` · `POST categories` · `PUT categories/{id}` · `DELETE categories/{id}` (409 `category_in_use`) · `GET categories/export` (CSV).
`GET product-display-order` · `PUT product-display-order/order {ids}` · `POST .../items {productId}` (404 `product_not_found`, 409 `already_in_display_order`) · `DELETE .../items/{id}` · `GET .../available-products?q&skip&take` · `GET .../quick-add-options` · `POST .../quick-add`.
Permissions copied from the Razor controllers: categories `Categories.View` (list, summary, details, export) / `.Create` / `.Edit` / `.Delete`; everything under display order `MainScreenProducts.Manage`.

## Decisions / differences from the Razor pages
1. **`MainScreenProductsController` (`api/MainScreenProducts`, the `MainScreenProduct` table) is not ported.** Nothing in the UI calls it and the POS grid reads `ProductDisplayOrder` (`MainProductsItemComponent`), so the *Product Display Order* page **is** the live "main-screen pinning". The legacy controller and table stay until cutover (Z) and can then be deleted (the demo seeder still fills the table).
2. **Categories have no colour/image/order.** The Razor create form shows Color / DisplayOrder / ImageUrl inputs, but the controller ignored them and the entity has none; the SPA form is name + description + active only.
3. **Create/edit are a dialog**, not separate routes (`/app/categories/new`, `…/edit` do not exist). Details is a route.
4. **Reorder** is `PUT order {ids}`; the server numbers rows 1..n in that order and keeps any row the client did not know about *after* the listed ones (so a stale list from a second user cannot create duplicate positions). The Razor page re-posted `IsActive=true` for every row; the API leaves `IsActive` alone.
5. **Drag and drop** uses `@dnd-kit` (new deps: core, sortable, utilities) with pointer + keyboard sensors, plus explicit **Move up / Move down** buttons (touch and screen readers), localized announcements, and a "leave without saving?" guard (router blocker + `beforeunload`).
6. **Add product** rejects a product already on the main screen (409). The old page only avoided it by hiding those products in the picker.
7. **Quick add keeps the old defaults** (category 1, supplier 1, brand 1, minimum stock 5, cost = 70 % of price, EAN-13 `2yyMMdd` + 5 random digits + check digit). It still needs only `MainScreenProducts.Manage` (as before, no `Products.Create`) — see the watch list.
8. Export is a GET (the Razor one was a POST with an antiforgery token).
9. The Razor "refresh" buttons are gone: lists refetch on mutation, window focus and after 30 s.
10. Category details: "View all products" links to the Products page through the session's nav `href` (SPA or Razor, whichever is live) with `?categoryId=`; the Razor Products page may ignore that parameter — C1 should read it.

## Watch list (pre-existing, not changed here)
- **No default role holds `Categories.Delete`** (not even Admin), so the delete button is a 403 on a fresh install in both UIs until the Users page grants it. The API test grants it to Admin through `IRoleAccessService` first and shows the role edit applies to an open session. Probably wants adding to Admin's defaults — a business-rule change, left for the owner.
- `Categories_Manage` exists but nothing checks it.
- Quick add hard-codes category/supplier/brand id 1: fails or mis-files on a database where those rows do not exist.
- Deleting a category uses the repo's hard delete; when products (including soft-deleted ones) still point at it the service throws and the API answers `category_in_use`.
- The top bar and `PageHeader` both render an `<h1>` (shell and 0C); tests scope to `main`.
- Playwright here needs `PW_CHROMIUM` (installed Playwright wants a newer Chromium than the machine has).
