## Behaviour (read this)
1. **The cart is only cleared after the server says yes.** The dialog sells a *snapshot* of what the server priced (`totals.input`, `totals.total`); a refusal keeps the dialog open with the server's localized message; the cart store is untouched either way.
2. **Lost connection = "Try again" with the same idempotency key.** No answer (status 0) or a 5xx shows "We could not confirm whether this sale went through…" and the same key is reused (`keyForSale`: same cart / customer / method / debt flag / total ⇒ same key; anything changed ⇒ new key, which avoids `idempotency_key_reused`). A sale on account stays on account on retry. Escape / Cancel are disabled while a request is in flight (a sale could otherwise finish unseen).
3. **`insufficient_stock`** → "Sell anyway / Review cart" (as before); "sell anyway" resends with `allowInsufficientStock` and the same key; "Review cart" closes the dialog.
4. **Typed total**: lower = discount (hint shows percent and amount like the old popup); the dialog refuses a figure the server would (greater of 1.00 / 2 %) before asking. Server `total_mismatch` is still shown if it happens.
5. **Cash**: methods with `requiresChange` show "Amount received", quick amounts (exact, then round figures scaled to the currency) and **Change due**; less than the total blocks Complete. The server does not know the amount handed over (the API has no field), so the change is display only, on the dialog and the success screen.
6. **Other currencies**: the dialog shows `≈` totals in the other active currencies (from P3's `totalsByCurrency`); the sale is made in the cart currency (switch it in the cart before paying).
7. **Drawer closed**: a warning banner with a link to `/cash-drawer/open` (it closes the dialog; the cart stays). It does **not** block: `requireOpenDrawer` is left **off** (P1 decision 2 — the old till sold anyway). Turning it on is one flag in `PaymentDialog.tsx` + a decision for you.
8. **Licence stopped**: the dialog shows "Sales are stopped" with a link to `/license` (also when the server answers `license_sales_stopped` mid-sale); the cart is kept. Browsing the catalog stays open as before.
9. **A resumed held cart that is sold is deleted from the held list** (best effort, silent). P3 flagged this as P4's call: the old till left it there, which invited selling the same cart twice. Remove the `heldCartId` block in `slot.tsx` to restore the old behaviour.
10. The payment method defaults to the shop's default; the Arabic UI shows method names as stored in the database (not translated).

## Dropped / not done (consciously)
- **Multi-tender (split payment).** The checkout API takes one `paymentMethodId`; a split would need a new API and a change to the checkout service (business rule). Not built.
- **Manager-PIN overrides.** Nothing in the old till or in the API asks for a manager PIN (it has no endpoint), so there is nothing to override. `ui/ManagerPinModal` is ready if a rule is ever added (e.g. selling below minimum stock, big manual discounts).
- **Credit-limit rules.** "as today" = none: the customer entity has no credit limit and the checkout service does not check one. Debt sales have no cap, same as before (see S3 notes on overpayment).
- **Customer list scrolling.** The picker loads the first 30 matches for what is typed (empty = first 30 by name) instead of the old infinite scroll; typing narrows it. The API still pages (`hasMore`), the control just does not ask for page 2.
- **Customer debt dialog (S3)** is not used here: the on-account *sale* is `addToDebt` in checkout; `<CustomerDebtDialog>` is the manual debt entry on the customers pages.
- **Receipt DTO / on-screen receipt preview**: the success dialog shows the essentials from `PosSaleDto`; paper and PDF stay server-side.
