## Endpoints
All list endpoints take `page,pageSize,sort,dir,q` (in-memory, these tables are tiny). Permissions are copied action by action:
- `currencies` — `GET` list/one/`POST convert` need `Currency.View`; `POST` = `Currency.Create`; `PUT` and `PUT {id}/default` = `Currency.Edit`; `DELETE` = `Currency.Delete`.
- `exchange-rates` (+ `GET suppliers` for the picker) — same permissions as the legacy `ExchangeRatesController`.
- `taxes` (+ `GET categories` for the picker, `POST {id}/default`, `POST {id}/deactivate`, `POST calculate`) — `Tax.View`; Create / Edit / Delete; `Tax.Manage` for default and deactivate (as the Razor `TaxController`).
- `discounts` — `Discounts.View`; every write `Discounts.Manage`. `payment-methods` — `PaymentMethods.View`; every write `PaymentMethods.Manage`.
- `code-lists` (+ `values`) — read needs `Settings.View` **or** `Settings.Manage`; writes `Settings.Manage`.
Errors: 400 `validation_failed` with the field (`code`, `rateToUsd`, `toCurrencyId`, `name`, `key`, `value`, `effectiveTo`, ...), 409 `currency_default_required`, `currency_inactive`, `currency_is_default`, `currency_in_use`, `discount_in_use`, `payment_method_system`, `payment_method_in_use`.

## Decisions / differences from the Razor pages
1. **Which `Tax`? (open question 13.4 answered).** The Tax page's entity is `Core.Entities.Products.TaxRate` (+ `Products.ITaxService`), which is what the SPA manages. The other one (`Sales.Tax`, `api/sales-taxes`, `Sales.ITaxService`) has no screen and no consumer anywhere; it is **not** ported. It can go at Cutover together with `TaxesController`. Neither affects the till (`POSCheckoutService` hard-codes `taxAmount = 0`) — the Tax page says so in a note.
2. **The Razor Currency page was mostly a mock-up.** Its exchange-rate table was a hard-coded LBP→USD row, "Add exchange rate" and both "Settings" forms posted to stubs that did nothing, and the stat tiles started from made-up numbers. The edit/delete buttons in its currency table had no handler. Now: real currencies table (add, edit, make default, delete), a real pair-rates table, three real tiles. **Dropped:** the auto-update-rates settings (no job exists to update anything) and the fake "last update" tile.
3. **Currency permissions fixed.** The Razor `CurrencyController` required only `Currency.View` for everything, so a view-only manager (the Manager role holds exactly that) could create, edit and delete currencies. The API asks for `Create` / `Edit` / `Delete` like the exchange rates always did. Behaviour change by design; tested.
4. **Rates are validated.** `RateToUSD` must be > 0 (the till divides by it), as must a pair rate; percentages are 0–100; the code is trimmed/upper-cased and unique ignoring case; the default currency must be active. The old endpoints took anything.
5. **"One default" is enforced everywhere.** Currency and tax services already moved the flag; the discount and payment-method services did not (a second default depended on row order), so the API clears the other defaults. A currency cannot be un-defaulted (409) — pick another one; the default cannot be deleted.
6. **"Customer Debt" is protected.** `POSCheckoutService` finds the system payment method behind "add to customer debt" by that name. The old API let anyone rename, delete or duplicate it, silently breaking debt sales. It is now listed (`isSystem`) but cannot be edited/deleted, and no other method may take the name. A name containing "cash" is what makes the till work out change — shown as "Gives change" so the effect of a rename is visible.
7. **Deletes that would orphan data say no.** Currency (suppliers, receipts, rates point at it) and payment method (receipts) answer 409 with a reason instead of a foreign-key 500; discounts likewise. The services hard-delete (`ISSoftDeletable`'s flag is not used by `Repository.DeleteAsync`) — unchanged.
8. **Pair rates (`ExchangeRate`).** One per (from, to, supplier). The unique index treats NULL suppliers as distinct, so the store-wide uniqueness is checked in the API. **Careful:** the till's own conversion (`PriceRules.ConvertViaUsd`, `PosPricingMath`) ignores `ExchangeRate` and uses each currency's `RateToUSD`; only `CurrencyConversionService` (cart/product prices on the old screens) reads pair rates first. The page says so. The converter card calls the till's `PosPricingMath.ToCartCurrency`, i.e. exactly what a cashier sees (USD bridge, banker's rounding to 2 decimals).
9. **Tax periods are whole days.** The date pickers give `yyyy-mm-dd`; the SPA sends `T00:00:00Z` for the start and `T23:59:59Z` for the end (the Razor page sent a bare date, which made "until 31 Dec" end at the *start* of 31 Dec). Dates are displayed by their UTC day, so they read the same in every time zone. Tax "deactivate" (Tax.Manage) switches it off and ends it now, as before.
10. **Code lists** had no UI. API gained what the legacy one lacked: add/edit/delete a value (the value service was injected and never called). Nothing in the app reads a code list yet (the page says so). Deleting a list deletes its values (FK cascade). `GET` also opens for `Settings.Manage` alone: the built-in Admin role holds Manage but not View, so with the legacy rule it could not read its own lists. (`Settings.View` is on Manager.)
11. **Supplier on discounts / payment methods / sales-taxes is not in the contract.** The legacy shapes took a `supplierId` nothing ever set or read; an edit keeps whatever a row already has.
12. **Audit:** requests are audited as `POST/PUT/DELETE Api.Currencies/...` etc.; entity changes (rate edits included) are recorded by the change tracker like for every entity. No explicit `AuditActions` existed for these screens.
13. **After a save the till's lookups are refetched** (`['pos', ...]` query keys) and the server-side lookup cache (`CacheKeys.Discounts` / `PaymentMethods`) is cleared by the existing services, so a new discount or method shows at the till without a restart (tested through `GET pos/discounts` / `pos/payment-methods`).
14. `ui/Modal` trap: a `<form>` around `ModalBody` + `ModalFooter` breaks the card's flex layout (tall bodies overflow and the footer leaves the viewport — found by Playwright on the tax dialog at 1366×768). The module's forms use `display: contents` (`.modalForm`). Not changed in `ui/` (frozen); worth fixing there at Cutover, then drop the class.

## Watch list (pre-existing, not changed here)
- The legacy `api/Currency`, `api/ExchangeRates`, `api/sales-taxes`, `api/Discounts`, `api/PaymentMethods`, `api/CodeLists` and `Tax/api/taxes` controllers are untouched (the Razor pages and anything else may still call them); all go at Cutover.
- `Currency.RateToUSD` is a `float`; the API exposes `decimal` (converted at the edge). 6 decimals are accepted; very large rates lose precision in the float — as before.
- `Manager` role holds `Currency.View` + `Tax.View` + Discounts/PaymentMethods manage + `Settings.View` — so a manager can now *see* currencies/taxes but, unlike on the Razor page, not change currencies.
- The Cashier role holds none of these permissions (checked in tests).
- `ApiPipelineTests` / `ApiConventionTests` use the first nav page that is not migrated as their example; today that is **Settings** (A2) — when A2 flips it they must pick Backup.
