## Endpoints
All need **`Settings.Manage`** — the class-level attribute of the Razor `SettingsController` — reads included. `Settings.View` alone is *not* enough (the legacy `api/AppSettings` controller let it read; that controller is not part of this API).
`GET settings/store` · `PUT settings/store` · `POST settings/store/reset` — the ten receipt fields (name, two address lines, phone, tax id, website, footer message, three footer lines).
`GET settings/printing` · `PUT settings/printing` — `receiptPrinterName`, `stickerWidthMm` (15–150), `stickerHeightMm` (10–150).
`GET settings/printers` → `{items}` printers installed on the machine running the server · `POST settings/printers/test {printerName}` → `{printed, message}` (an unreachable printer is `printed:false` with 200, as the Razor page showed it as a message, not an error).
`GET settings/branding` · `PUT settings/branding` (`multipart/form-data`: `appName`, `logo`, `favicon`, `removeLogo`, `removeFavicon`; every part optional) → `BrandingSettingsDto` (custom name, default name, flags, cache-busted image URLs, limits and allowed extensions so the UI does not hard-code them).

## Decisions / differences from the Razor pages
1. **The landing page of three cards is a tab bar** (Store & Receipts | Printers & Labels | Branding), one route per tab.
2. **Dropped (no UI ever called them):** the generic `SettingsController` actions `GetByCategory`, `GetSetting`, `UpdateSetting`, `UpdateBulk`, `ResetToDefaults`, `Export`, `Import`, `ValidateSetting`, `GetSettingValue`, `InitializeDefaults`, and the whole legacy `api/AppSettings` controller (list / get / typed value / create / update / delete of raw key-value rows). Nothing in `Views/` or `wwwroot/js` references them. They die with the Razor controllers at cutover.
3. **"Language defaults" (the plan's list) is not offered:** `StoreSettings.DefaultLanguage` / `AppSettingsDTO.DefaultLanguage` are stored but read by nothing; the service says as much and a save leaves them alone. The user's language is client state (D8).
4. **What a store save touches** is unchanged: only the ten receipt fields (+ `LastModifiedByUserId`); email, currency symbol, logo path, return-policy days, tax/barcode toggles, social and registration number are left alone. Reset-to-defaults still resets *every* column (service behaviour kept).
5. **Printing save:** reads the stored `AppSettingsDTO`, changes the three fields and calls `UpdateAppSettingsAsync` (which writes only those three), so the other stored app settings are untouched — tested. **New:** the sticker size range is enforced on the server (the Razor form had `min`/`max` in HTML only; the client's `clampWidth/clampHeight` clamp anyway).
6. **Branding save:** both files are checked (type, 2 MB) **before anything is written** — the Razor action saved the name first and could then fail on a file, leaving a half-applied brand. A name over 40 characters is now a 400 on `appName` (it used to be silently cut). The messages are localized (`Set_FileTypeNotAllowed`, `Set_FileTooLarge`, `Set_NameTooLong`); the UI also checks type and size the moment a file is picked.
7. **The shell is told at once:** a branding save invalidates the `session` query, so the rail / top bar / favicon links take the new name and logo without a reload (verified in Playwright). The images are cache-busted by `BrandingService.Version`.
8. **Sticker printer (this computer)** stays a per-computer choice in `localStorage` (`nexpos-sticker-printer`, the key the C1 label dialog reads), saved the moment it is picked, listed by the desktop app only (`electron.listPrinters()`); in a plain browser the select is disabled with the old "desktop only" text. It imports `getPrinterName` / `setPrinterName` from `modules/products/labels/stickerLabel` rather than copying them.
9. **Receipt printer is the server's printer**, as before: the list comes from the machine running the host (in the installed app that is the till). A configured printer that is not detected right now stays in the list as "(not detected)" so a save does not drop it.
10. **Receipt preview** follows the form like the Razor one, now also localized (it was hard-coded English) and with phone / tax id / URL / date isolated left-to-right so Arabic text does not scramble them. It is an illustration; the real slip is built by `EscPosService` on the server.
11. **Save buttons are disabled until something changed**; the store form re-syncs from the server unless the owner is mid-edit.
12. Audit: requests are audited as `PUT/POST Api.Settings/...` by the middleware; the Razor controller wrote no explicit entry either, so none was added.

## Not done / not verified
- **A real receipt printer** was not exercised: Test print and the receipt-printer list were checked against the demo printer only. By hand, on the till: open Printers & Labels, pick the real printer, press Test, expect a slip; unplug it and press Test again, expect the "Could not print…" message and no error page.
- **The sticker-printer select inside the desktop app** (`window.nexpos.listPrinters`) was not run in Electron; in a browser it shows disabled as designed. By hand in the installed app: pick a printer, open a product's "Print label", expect the same printer preselected.
- Licence-stopped and idle-timeout behaviour are inherited from the shell: these are not sales routes, so a stopped licence leaves them open (as the Razor ones were).
- Branding was not tried with an SVG / ICO upload or with a real 2 MB file over HTTP (the size rule is tested with a 2 MB + 1 byte body; type rules with `.gif`).
